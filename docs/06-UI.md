# AppShell UI / interaction specification

## Philosophy

Minimal, compact, dark-first, keyboard-operable and consistent between Python and PowerShell; do not turn AppShell into a design-system project. Reuse NativeHTMLKit UI's existing cobalt/theme/density mechanics. No white-only default, no frontend framework, no JavaScript. Shell-owned styles can address its compact sidebar and input-column defect locally; do not fork SDK/UI.

## Fixed window structure

```
+-------------------------------------------------------------+
| AppShell                                      [Settings] [?] |
+---------------+---------------------------------------------+
| Home          |  [Title / breadcrumbs]                       |
| Extensions    |  [Action/refresh toolbar]                    |
|               |                                             |
| Installed     |   <<validated dynamic page content>>         |
|  Hello        |                                             |
|  System Info  |                                             |
|               |                                             |
+---------------+---------------------------------------------+
|  Optional slim error / restart-required status              |
+-------------------------------------------------------------+
```

- Topbar: application name, optional active page name, Settings/Extensions route and keyboard focus.
- Sidebar: always-present Home / Extensions / Settings, plus sections/pages of enabled extensions only; stable sorted by extension title, page order, page ID; collapse long lists. Failed/pending extensions shown under Extensions, not dead navigation links.
- Content: a single SDK-owned dynamic outlet inside the mounted UI. Validation errors render shell-owned error pages.
- Status: small restart-required indicator when changed; no upgrade or install takes effect in current process.
- Settings: `Open extensions folder`, `Open data folder`, `Export diagnostics`, `Safe mode next launch`, host/runtime/platform info, default compact/comfortable density.

## Extensions page

Columns: Name, Language, Version, Status, Source, and controls. Only one language appears in each edition (Python or PowerShell); the language badge is informational. Actions: `Add extension`, `Open folder`, `Disable/Enable (after restart)`, `View logs`, `Remove (after restart)`, `Restore previous` when applicable.

`Add extension` v0.1 offers a native file/folder path or a package source string. Display `This package may execute code with your user privileges; install only from trusted sources` for user-initiated downloads. Copy the local source (or record a pinned registry source) without importing or installing it into any live runtime. Show `Ready — restart AppShell to install and activate`; package resolution and dependency preparation occur on the next startup. Do not add package-list cards, ratings, sponsorship, accounts or marketplace recommendations in v0.1.

Optional static catalog may be added later as an ordinary JSON file loaded on request; every entry is a package identifier and a URL, not an execution permission.

## Rendering controlled view descriptions

- Render semantic blocks with standard NativeHTMLKit HTML/CSS. Every extension-supplied string is HTML-escaped; fields are validated and can only cause host-approved DOM primitives.
- Generate stable event IDs unique for each `(extension_id, page_id, generation, local_node_index)`. Store a host-owned mapping from native element id to declared command and params. Never execute code snippets from JSON and never trust CSS classes as command identities.
- Use one document-level click/submit subscription; reconstruct correct `values` by invoking `form_data` on the host-owned form element when a button is clicked. The element ID is generated by host.
- Input/change can be left local until explicit command submit. This avoids frequent worker IPC for each keystroke and preserves typing/focus.
- Replace the dynamic outlet on page navigation and explicit refresh. Do not replace every second during user edits. Preserve pagination/selection when reasonable; loss of unsaved changes should prompt before navigation if actual form state diverges from initial values (can start with warning only for actions where loss is likely).
- Read-only table: compact, alternating/subtle rows, no arbitrary HTML, no virtualization; 200-row limit. For larger datasets, extension should provide a filter or later pagination API.
- Action button: lookup declared command. `read` executes; `write` and `destructive` get native modal confirmation; while running, disable conflicting commands and show busy; success can refresh or show message.
- Content limit/errors must be visible as meaningful status, not silent clipping.

## Thread/runspace rules

**Python:** UI library's owner thread applies view updates; workers and IPC are background I/O. Use `ui.post()` to update shell state/document. Do not mutate state directly from a worker thread in ways that trigger known UI `Computed` concurrency defect.

**PowerShell:** UI library's owner runspace processes native events via `Wait-NativeHTMLKit`. Blocking extension calls **must not** occur in click handlers or owner runspace; worker I/O runs asynchronously and delivers result back to the owner runspace through the public SDK task/event handoff mechanism. `Start-NativeHTMLKitTask` executes in a fresh runspace and doesn't inherit script modules/variables, so explicitly pass serializable arguments and import helper code there as needed. Keep real UI state updates in owner runspace.

## Accessibility and keyboard acceptance

- Tab order: main nav → toolbar → form controls → action buttons; Enter/Space work; focus restored to appropriate heading or control after navigation; visible focus styling.
- Error/confirmation announcements rely on native HTML semantics. Verify with a real screen reader; do **not** assert screen-reader compliance based only on headless tests. Core's known Linux Orca select-value announcement issue is open.
- Test 100% as initial gate on Linux KDE Wayland and Windows; add 125/150% scaling, IME entry and keyboard routes as release qualification, since UI 0.1.1's latter checks were not rerun on all newest builds.
- Test no `stale document` errors, no click dispatch to previous page, no duplicate callbacks after 100 navigations.

## Intentionally not implemented

No dockable panels, VS Code-like multi-window workspace, independent extension themes, visual designer, drag-and-drop layout editor, webview, browser extension execution or live custom extension markup. A separately trusted host-side UI adapter is only a future opt-in after specific use cases prove the standard view insufficient.
